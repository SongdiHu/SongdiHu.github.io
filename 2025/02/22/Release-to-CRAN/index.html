How to Release an R Package to CRAN

Background

The last few months, I’ve been focused on developing and releasing an R package. This toolkit was created based on a study by Dr. Romanescu. Many newcomers, myself included, often feel overwhelmed when it comes to properly releasing a package after preparing the code. Here is a concise introduction to address the question, “How?”

Link to the released package: https://cran.rstudio.com/web/packages/REffectivePred/index.html

1) TL;DR

  • Write clear docs for every exported function/dataset (Rd files) and a package-level help page; add a vignette if helpful.
  • Ensure policy compliance: fast examples, no writes outside temp dirs, graceful handling of network failures, portable code.
  • Pass R CMD check –as-cran locally and on multiple platforms (win‑builder, R‑hub).
  • Submit via the CRAN web form (or devtools::release()), then respond promptly to reviewer emails.

2) Documentation Requirements

Help pages (Rd): One per exported function/object and per dataset, with title/description/usage/arguments/value/examples.
Package help page: So ?yourpkg works (alias yourpkg-package).
Vignettes: Strongly recommended; show real workflows (declare VignetteBuilder).
README & NEWS.md: Installation/quick start; user‑visible changes across versions.
CITATION (optional): Provide a bibliographic entry in inst/CITATION if you want users to cite your package.

Examples must be: fast (seconds), deterministic, non‑interactive; avoid network or fail gracefully; write only to temp dirs and clean up.

3) Prepare the Package

  • DESCRIPTION: Single maintainer email; meaningful Title/Description; valid License; URL/BugReports; use Authors@R.
  • NAMESPACE: Export the right symbols; import minimally; register S3/S4 methods.
  • Dependencies: Use public APIs only; declare Imports/Suggests appropriately.
  • Tests/CI: Add testthat; configure GitHub Actions (Linux/macOS/Windows) for checks.
  • Performance: Keep examples/vignettes/tests quick; gate long parts behind if (interactive()) or skip on CRAN.

4) Pre‑Flight Checks

  • Local: R CMD check --as-cran (or devtools::check()); eliminate all ERRORs/WARNINGs and significant NOTEs.
  • Windows: win‑builder (devtools::check_win()).
  • Multi‑platform: R‑hub (v2) runners via the rhub package (devtools::check_rhub()).
  • Keep a small cran-comments.md summarizing environments and check results.

5) Submission

  • Option A: Web form - Upload the source tarball, confirm the email, monitor incoming and your inbox.
  • Option B: From R - devtools::release() builds, checks, and submits (still sends a confirmation email).

After submission: Reply promptly (plain‑text). For routine updates, avoid very frequent small releases; be considerate of reverse dependencies.

6) Common Pitfalls

  • Slow examples/vignettes/tests → keep fast; mark long parts optional.
  • Writing outside temp dirs → always use tempfile()/tempdir(), clean up with on.exit(unlink(...)).
  • Fragile internet access → wrap with timeouts/tryCatch(); do not error when offline.
  • Missing docs → no exported object without an Rd page; provide a package help page.
  • Non‑portable code/private APIs → use public R API; avoid OS‑specific behavior unless guarded.
